# Local Paper recovery

Implemented against the current working tree and the Paper/account-binding follow-up in `functional-architecture.md`. Paper never submits orders to an external venue. SQLite `finalizePaperFill` commits the fill fields and wallet in one immediate transaction. There is no external execution to reconcile: a persisted filled order already includes its wallet effect; created/submitted/unknown cannot be filled again during recovery.

`GET /api/paper/recovery` returns every pending created/submitted/unknown intent across accounts (including unbound legacy rows), independently of recent-history limits, plus persistent recovery audits. Both the Legacy pair wallet and New shared spot wallet show the same Recovery panel beneath the ticket, including original account IDs. Replay uses its own ticket and does not show normal Paper recovery controls. MCP workspace context exposes the same information read-only; it has no new execution, confirmation or recovery tool.

`POST /api/paper/recovery` accepts exactly `{ action: "cancel", clientOrderId, actionId, reason }`. The local API Host/Origin/JSON guard applies. Prices, balances, fill claims and extra fields are rejected. Normal Paper submission and preview confirmation also reject extra fields. The UI requires a reason and retains the same action ID and reason when retrying a lost response.

One immediate transaction checks the saved intent, cancels it and inserts a unique audit containing the action ID, original nullable account ID, prior status, outcome, operator reason, review flag and timestamp. Wallets are never initialized, written or repriced by recovery. Exact retry returns the saved audit; changed reason/action ID or cross-order action-ID reuse fails. Filled/rejected/cancelled orders without a matching recovery audit cannot be recovered. If a fill wins the transaction race first, recovery fails and preserves the committed fill; if recovery wins, finalize sees cancelled and cannot book the late quote. A late quote failure cannot change cancelled back to unknown either.

Compatibility: no order-status enum change. The existing cancelled state is now a safe terminal state for recovery from created/submitted/unknown. An additive `paper_recoveries` table is created by the existing atomic, restart-idempotent migration. Existing orders, previews and balances are untouched. Legacy ownership stays NULL. Missing accounts or unexpected saved fill price/fee on pending orders require manual review; cancellation fences further execution but does not assert reconciliation or repair historical money. Review records remain visible; this slice does not implement a manual balance-adjustment or review-dismissal API. Confirmed preview status continues to mean the human decision was saved; the linked order and recovery audit report its execution/cancellation outcome. Recovery is explicit, never a startup sweep or automatic re-quote. A new trade requires a new human action and order ID.
